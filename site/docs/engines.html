Analysis engines

Scan64 analyses with one UCI engine selected by configuration. The Docker image and the desktop app bundle Stockfish 18, Caissa 2.0 and Arasan 26.1 (Bundled engines). A fresh install of either analyses with Caissa and plays the bot ladder with Arasan; an install from before keeps Stockfish (Which engines an install uses). A source checkout uses Stockfish on PATH. Any other open-source UCI engine can replace them for analysis, review, hints, lessons and narrator evidence without a code change.

Bundled engines

Each engine is built from its pinned source archive. Every source archive, network and downloaded licence has a SHA-256 in the Dockerfile, and scripts/build-server.py reads the pins from there, so a desktop build accepts nothing the image would not. Source archives and licence texts ship next to each executable (THIRD_PARTY_NOTICES.md).

Engine Role (#396) Network Docker image Desktop resources
Stockfish 18 (GPL-3.0) installs from before the bundled engines two NNUE files, embedded /usr/local/bin/stockfish stockfish/stockfish[.exe]
Caissa 2.0 (MIT) analysis eval-ml-8-152B-spsa.pnn, embedded through EVALFILE /usr/local/bin/caissa caissa/caissa[.exe]
Arasan 26.1 (MIT) bot ladder arasanv8-20261005.nnue, loaded from the executable's directory /usr/local/lib/arasan/arasan arasan/arasan[.exe] next to the .nnue

Each package carries one profile for each permissive engine (sources in config/engines/container/): caissa.toml (UCI_ShowWDL on) and arasan.toml (OwnBook off, the elo ladder of config/engines/arasan.toml). The image has them in /usr/local/share/scan64/engines/. The desktop build stages them in engines/ among its resources, with binary_path rewritten to the engine beside them (../caissa/caissa[.exe]).

Provisional score scale. caissa.toml sets no score_scale, so a fresh install reads Caissa's centipawns as Stockfish's. The committed measurement (caissa_positions_report.md, Evaluation) puts them at 0.71–0.75 of Stockfish's (1M-node searches pooled, n = 37): win percentages and the 150 cp mistake threshold run on an uncalibrated scale, and won positions read near 600–700 cp where Stockfish reports 1,000 or more. The earlier #396 comparison (1 s searches, n = 31) found the opposite, a slope of 1.19, so no single factor fits both samples yet. The fit on the 50 narrator positions is open on #396. Installs that keep Stockfish are unaffected.

Which engines an install uses

A package names its profile folder in SCAN64_BUNDLED_ENGINES_DIR: the image sets it, and the desktop shell passes it. On the first start with that folder and no engine configured, the server records the install's engines in <database>.engines.toml next to its database (/data/scan64.db.engines.toml in the image, scan64.db.engines.toml in the desktop data folder):

At first start Recorded Analysis Bot ladder
no database yet (a fresh install) engines = "bundled" Caissa Arasan
a database already there engines = "stockfish" Stockfish Stockfish

Every later start reads the record, so an update never changes an install's engines: games under way, bot sessions (each plays only under the ladder it started with) and stored analysis keep the engine they were made with.

To switch an install, stop it and edit the record ("bundled" or "stockfish"); in the desktop app the record is the only switch, because the shell starts its server with a cleared environment. In a source run or the image, SCAN64_ENGINE_CONFIG or SCAN64_LADDER_ENGINE_CONFIG set explicitly always win, and so does SCAN64_STOCKFISH_PATH in the image. Nothing is recorded on such a start. In the image:

docker run -e SCAN64_ENGINE_CONFIG=/usr/local/share/scan64/engines/caissa.toml \
  -e SCAN64_LADDER_ENGINE_CONFIG=/usr/local/share/scan64/engines/arasan.toml ...

Under the Caissa profile alone bot play is unavailable, since Caissa has no strength options. Switching the ladder engine ends a bot session started under the old one with 503 bot_play_unavailable on its next move.

Every desktop installer check (scripts/desktop-package-smoke.py) requires the three engine folders and engines/ with both profiles, checks every pinned file against its Dockerfile digest, and starts each engine outside its own folder: it must report its id name and answer uci and isready.

Selecting an engine

Variable Default Effect
SCAN64_ENGINE_CONFIG unset Absolute path of an engine profile (TOML). When set, it fully defines the engine.
SCAN64_STOCKFISH_PATH stockfish on PATH Stockfish binary used when no profile is selected. Ignored when SCAN64_ENGINE_CONFIG is set.
SCAN64_LADDER_ENGINE_CONFIG unset Absolute path of a second profile that plays the bot ladder's moves. Unset, they use the analysis engine.

Without a profile the engine is Stockfish from SCAN64_STOCKFISH_PATH, one thread, 16 MB hash, no extra options: the same identity as before profiles existed, so saved analyses keep matching.

A profile:

[engine]
name = "ethereal"                                  # label for logs; not part of cache identity
binary_path = "~/.local/opt/engines/Ethereal.exe"  # absolute (~ expands), relative to this file, or a bare command on PATH
protocol = "uci"                                   # optional: "uci" (default) or "xboard"
threads = 1                                        # sent as Threads when the engine declares it
hash_mb = 16                                       # sent as Hash when the engine declares it
node_scale = 1.0                                   # optional, in (0, 1]: nodes sent = budget × node_scale
search_deadline_s = 120                            # optional, > 0: wall-clock bound on node/depth-only searches
score_scale = 1.0                                  # optional, > 0: engine centipawns per Stockfish centipawn

[engine.options]          # extra UCI options; each must be declared by the engine
UCI_ShowWDL = true

[limits.hint]             # optional per-use override (nodes and/or time_ms, multipv; no depth)
nodes = 200000
time_ms = 1500
multipv = 4

[ladder]                  # optional: how the bot ladder weakens this engine
strength = "elo"          # "skill" (default) or "elo"
elo = [1000, 1200, 1400, 1600, 1800, 2000, 2200, 2500]  # UCI_Elo for levels 1-8, increasing
movetime_ms = 500         # fixed time per bot move; required with "elo", rejected with "skill"

Examples: config/engines/ (ethereal.toml, berserk.toml, stockfish-wdl.toml, arasan.toml).

Rules (all enforced at load or engine start, failing with the file and key):

  • Unknown tables/keys, a missing or relative profile path, and non-positive numbers are rejected.
  • A binary_path without a directory (stockfish) is looked up on PATH. A relative binary_path with a directory (../caissa/caissa) is resolved against the profile file's own folder.
  • engine.options may not set Scan64-managed options: Threads, Hash, MultiPV, Ponder, UCI_AnalyseMode, UCI_Chess960, UCI_Variant, UCI_Opponent, UCI_RatingAdv, Skill Level, UCI_LimitStrength, UCI_Elo, and the XBoard cores and memory.
  • An option in engine.options that the engine does not declare stops engine start with EngineConfigurationError.
  • Threads/Hash are sent only to engines that declare them (Lc0 has no Hash).
  • The only per-use override today is hint (interactive hints; it still runs inside the three-second hint deadline). Review (10,000 nodes), focused passes, lesson verification and mate-source searches keep the budgets in their callers.
  • engine.node_scale (default 1) scales every node budget Scan64 sends to this engine: game analysis, focused passes, hints, lesson verification, Analysis Board lines, the bot ladder and Skill Level play. The budgets are sized for an alpha-beta engine's nodes/second; an engine with slow neural nodes (Lc0, Maia-3) sets a value below 1, for example 0.002 so that a 1,000,000-node focused search sends 2,000 nodes. The engine receives at least 1 node. Stored rows keep the Scan64 budget in nodes and record node_scale when it is not 1, so rows from different scales never reuse each other; rows at scale 1 keep their pre-existing reuse key.
  • engine.search_deadline_s (default 120) bounds every analysis search that has no time limit of its own (fast pass, focused pass, lesson verification, Analysis Board lines). Past it the search is stopped and the request fails with EngineCapabilityError saying the engine did not finish its node or depth limit: an engine that ignores go nodes (Rodent V 1.2) reports unavailable instead of hanging. It is not part of the cache identity.
  • A pooled engine whose process exits (EngineTerminatedError) fails that request and is replaced: the next checkout from the pool starts a new process.
  • engine.score_scale (default 1) is the engine's centipawns per Stockfish centipawn. Scan64's win-probability curve (Lichess logistic) is fitted to Stockfish, so every win probability divides a line's score_cp by it first; stored score_cp stays the engine's own number. Each stored line and the row's identity record score_scale when it is not 1, so rows at different scales never reuse each other and rows at 1 keep their pre-existing reuse key. Other centipawn thresholds (the 150 cp fast-pass swing, narrator facts) still read raw score_cp.
  • engine.protocol = "xboard" runs an XBoard (protover 2) engine. The engine must declare ping and setboard; one that sends setboard=0 (Fairy-Max 5.0b) fails at start with EngineCapabilityError, since every Scan64 search starts from a FEN. Scan64 sends engine.threads as cores and engine.hash_mb as memory when the engine declares smp/memory. XBoard has no MultiPV, so only single-line searches work: game review and single-line analysis run; a search for more lines (focused passes, Analysis Board lines, hints with MultiPV, the bot ladder) raises EngineCapabilityError naming the engine, never a single-line substitute. Stored rows record protocol = "xboard"; UCI rows omit the key.
  • Any request the active engine cannot serve answers HTTP 503 with {"detail": {"code": "engine_capability_unavailable", "message": ..., "reason": ...}}; reason names the missing option and the engine. A background analysis job that hits it ends failed with that reason as its error.
  • The profile file is re-read when its modification time or size changes; a running pool keeps the processes it started with.
  • [ladder] selects the bot ladder's strength path. skill (the default, and the only path without a profile) searches every legal move at full strength and picks a move inside the level's error budget, seeded per session; it needs MultiPV, Skill Level and UCI_LimitStrength. elo sets UCI_LimitStrength = true and the level's UCI_Elo, then plays one move in movetime_ms with the engine's own randomness (not seeded; the session's node budget is unused). It needs UCI_LimitStrength and UCI_Elo; a level's UCI_Elo outside the range the engine declares fails the move with EngineCapabilityError (a 503 the player can act on, not a server error). The elo values are what Scan64 sends, not a measured playing strength. The analysis reset turns UCI_LimitStrength off again before every search. Sessions record the path in bot_policy_version: stockfish-error-budget-v1 for skill, uci-elo-v1:<engine name>:<elo list>:<movetime>ms for elo. A session plays only under the policy it recorded: when the server's [ladder] or engine changes while a bot game is open, the next bot move fails with EngineCapabilityError naming both policies, so a game is never counted in one strength cohort and played under another. Sessions without a recorded policy predate the Elo path and play only under stockfish-error-budget-v1. The opponent's name comes from the recorded policy: Arasan (level 1: First steps) for an Elo session on the arasan profile, Stockfish (...) for error-budget and unstamped sessions.

What every stored line contains

EngineAnalysis.raw_result is one dict per MultiPV line, best first. Keys appear only when the engine reported them (never null):

Key Meaning
pv Full principal variation, UCI moves.
score_cp / score_mate Score from the side to move (exactly one).
wdl [wins, draws, losses] per mille from the side to move.
depth, seldepth Nominal and selective search depth.
nodes, nps Nodes searched and speed. nps depends on wall-clock time; never compare or key on it.
multipv 1-based line index.

Rows written before this extension contain only pv and a score. They load unchanged; EngineAnalysis.lines() returns typed EngineLine values whose extended fields are None for them. No migration is needed: the column is JSON.

Stockfish reports WDL only with UCI_ShowWDL = true (see config/engines/stockfish-wdl.toml). That option is part of the engine identity, so WDL-enabled rows never reuse WDL-free rows and vice versa.

Cache identity

Batch reuse (scan64/chess/analysis/reuse.py) and the per-process hint cache are keyed on the effective engine inputs:

  • engine_version: SHA-256 of the executable (embedded networks included).
  • network: SHA-256 of external network/weights files named by EvalFile, EvalFileSmall, WeightsFile or Arasan's NNUE file when those files exist. A relative path is resolved where its engine loads it: the working directory, then the executable's directory, for the first three; only the executable's directory for NNUE file (Arasan 26.1 globals.cpp).
  • options: every UCI option value the process holds after configuration, including profile options, with the full-strength overrides applied.
  • nodes, depth, time_ms, multipv and the full FEN.

A different engine has a different executable digest and option set, so it never matches a Stockfish row, even if it reports the same id name. This is covered by tests/unit/test_engine_config.py (key separation) and tests/integration/test_second_engine.py (Stockfish rows, then Ethereal rows for the same owner and positions: no reuse). The profile name is not part of the key. The hint cache key includes the profile fingerprint (name, binary, threads, hash, options) and the effective hint limits.

The skill ladder stays Stockfish-only on purpose: its error budgets, SKILL_POLICY_VERSION = "stockfish-error-budget-v1" and the strength estimate cohorts (api/strength.py) are defined against Stockfish. An engine with UCI_Elo but no Skill Level (Arasan 26.1) plays the ladder through [ladder] strength = "elo". Without SCAN64_LADDER_ENGINE_CONFIG, opponent moves come from the same interactive pool as hints, under the analysis profile's [ladder]. With it, ladder moves come from a pool of the ladder profile's engine (sized like the interactive pool) under that profile's [ladder]; the analysis profile's [ladder] is then unused, scan64-cli serve checks the ladder profile's binary too, and the default batch pool shrinks by the ladder pool's engine threads. Analysis, hints, review and legacy Skill Level sessions (no bot_level) never use the ladder profile. A ladder profile with the same engine and [ladder] as the analysis profile adds no pool. Setting or changing it changes the server's ladder policy, so bot games started before cannot continue (the policy check above). Example: Caissa for analysis, Arasan for the ladder:

SCAN64_ENGINE_CONFIG=/path/to/caissa.toml SCAN64_LADDER_ENGINE_CONFIG=/path/to/arasan-ladder.toml uv run scan64-cli serve

When the engine that plays bot moves (the ladder profile's, else the analysis profile's) can play neither ladder, bot play is unavailable; play never falls back to Stockfish. The play endpoints (POST /v1/play-sessions when the bot moves first, …/moves, …/resume and …/opponent-move) return 503 with detail = {code: "bot_play_unavailable", message, reason}. reason is the EngineCapabilityError text that names the missing options. The player's move stays committed; a bot-first session is not created. The web client shows that bot play is unavailable under the active engine profile.

Chess variants (#398)

Scan64 reads variant positions with python-chess's variant boards: crazyhouse, three-check (3check), atomic, antichess, king of the hill, horde and racing kings. Searching one needs an engine that declares the variant. Which engines do, how python-chess selects the variant, installing Fairy-Stockfish and its probe results are in "Variants" below; this section is what Scan64 does with them.

  • API. POST /v1/analysis/position takes an optional variant (the names above; default chess). The FEN is parsed under that variant's rules: a FEN that is not a position of the variant is a 422 before any engine access. The reply names the variant it was searched under. The explanation endpoint covers standard chess only and rejects any other variant with 422.
  • Engine check. Before any search (see "How the variant is selected"), Scan64 compares the board's variant with the engine's declared variants: the UCI_Variant choices over UCI, or the variants feature over XBoard, where antichess is giveaway. An undeclared variant is an EngineCapabilityError, answered as 503 engine_capability_unavailable whose reason names the variant and Fairy-Stockfish. Without the check python-chess raises a plain EngineError, which the endpoint reports as a generic analysis failure.
  • Hint cache. The cache key includes the variant: the same FEN is a different position under another variant's rules.
  • Not covered. Diagnosis, lessons, puzzles, the narrator's explanations, bot play and position health read standard chess only.
  • Tests. The tests use the fake UCI engine (tests/fixtures/engines/fake_uci.py, FAKE_UCI_VARIANTS), which plays by python-chess; no test runs Fairy-Stockfish. The probe in "Variants" runs it directly, not through Scan64's endpoints.
  • Variant games. A PGN with a supported Variant tag is stored with its variant. Game analysis, review and backfill refuse it with 409 variant_not_covered; the web import says the game is saved and not analysed, and Your Games labels it ", not analysed".

Then point a profile at the binary (for example config/engines/ethereal.toml) and set SCAN64_ENGINE_CONFIG. tests/integration/test_second_engine.py runs a stored game through the production analysis job and the hint pool with Ethereal (or SCAN64_TEST_SECOND_ENGINE). Tests never read the developer's engine selection: an autouse fixture in tests/conftest.py removes SCAN64_ENGINE_CONFIG, SCAN64_LADDER_ENGINE_CONFIG and SCAN64_STOCKFISH_PATH before every test, so tests that run Stockfish use the stockfish on PATH. A test that needs a profile or a Stockfish path sets it itself. SCAN64_TEST_SECOND_ENGINE is a test input and is kept.

How CI provides the second engine

CI does not build a second engine. The Run repository quality gate step in .github/workflows/ci.yml sets SCAN64_TEST_SECOND_ENGINE to tests/fixtures/scripted_uci_engine.py:

Property Value
id name Scan64 Scripted UCI Fixture (does not start with Stockfish)
Declared options Threads, Hash, MultiPV only (no Skill Level, no UCI_Elo)
Moves and scores Legal moves only; two-ply material search; mate 1 for a mating move
Each info line depth, seldepth, multipv, score, nodes, pv
Engine identity The sha256: digest of the script file, so its rows never match Stockfish rows

The fixture checks the configuration path, the stored line fields and cache separation. It does not check chess strength or the score scale of a real engine.

With CI set (GitHub Actions sets it), the tests do not skip. A missing second engine or Stockfish fails both tests. A SCAN64_TEST_SECOND_ENGINE path that is not a file fails the tests everywhere.

Why not Ethereal in CI: the Ethereal build above (commit 0e47e9b, classical, gcc -O3 -DUSE_POPCNT) passes both tests locally. On the GitHub ubuntu-latest runner (AMD EPYC 9V74) the same build crashed with a segmentation fault on its first go. The engine pool then did not shut down, and the job hung for 45 minutes. An -O1 ASan build did not crash there, so the cause is not found.

Engine compatibility set

benchmarks/engines/compat.py runs every engine in compat.toml through Scan64's own features, each at its production entry point and budget, and records one of: works; unavailable (an EngineCapabilityError, with its exact reason, which the API returns as 503 engine_capability_unavailable); blocked (the focused pass, when game analysis did not work); error (any other exception: a bug). How the variant is selected

The board selects the variant. python-chess sends UCI_Variant before every search from the type of the board it is given (CrazyhouseBoard sends crazyhouse) and raises EngineError: cannot set UCI_Variant which is automatically managed when a caller sets it. UCI_Variant is therefore one of the Scan64-managed options a profile may not set (see the rules above); a variant engine's profile is an ordinary profile. Before a search, read the values the engine declares (engine.options["UCI_Variant"].var). Without that check python-chess raises EngineError ("engine does not support UCI_Variant" for an engine without the option, "invalid value for combo option 'UCI_Variant'" for a value it does not list), not a capability message.

What Scan64 lacks for variants

Tracked in #398:

  • Narration: the explanation endpoint refuses a variant with 422.
  • The variant Analysis Board cannot load a FEN or an imported variant game; it starts from the variant's start position.
  • Game analysis (ingest_pgn raises NonStandardVariantError), review, diagnosis, lessons, puzzles, bot play and position health stay standard chess; variant games are stored, labelled and refused with 409 variant_not_covered.
